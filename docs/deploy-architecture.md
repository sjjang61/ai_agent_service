# 웹앱 배포 아키텍처

에이전트가 sandbox 에서 만든 웹앱(정적 빌드 결과 또는 API 서버가 있는 앱)을 사용자가 브라우저로 열 수 있게 배포하는 기능의 설계 기록이다.
무엇을 만들었는지뿐 아니라 **어떤 대안을 검토했고 왜 지금의 방식을 골랐는지**, 그리고 **아직 남아 있는 검토 과제**를 함께 적는다.

- 구현 커밋: `f5f742e` (배포 기능), `a4d8f6e` (채팅 우측 iframe 미리보기)
- 관련 문서: [sandbox-isolation.md](sandbox-isolation.md)

---

## 1. 요구사항

1. sandbox 안에서 빌드가 끝난 앱(`dist` 등)을 외부(브라우저)에서 접근할 수 있어야 한다.
2. 앱이 **여러 개** 동시에 있을 수 있다. 포트는 **20000 부터 순차적으로** 할당한다 (범위 예: 20000~20100).
3. **API 서버가 있는 앱**(Node/Python 백엔드, 풀스택)도 배포할 수 있어야 한다. 정적 파일만으로는 부족하다.
4. 포트와 앱의 **매핑 정보를 관리**하고, 컨테이너가 꺼져 있어도 **요청이 오면 다시 살아나서** 연결되어야 한다.
5. 호스트(localhost)의 별도 프록시 포트를 통해 접속한다.

## 2. 출발점: 현재 구조의 제약

| 사실 | 영향 |
|---|---|
| sandbox 컨테이너는 포트를 게시하지 않는다 | 호스트에서 접근할 경로가 없다 |
| 개발 환경의 백엔드는 호스트(macOS)에서 직접 실행된다 | Docker Desktop 에서는 호스트가 컨테이너 IP 로 접근할 수 없다 → 포트를 **컨테이너 생성 시점에** 게시해야 한다 |
| 컨테이너에는 생성 후 포트를 추가할 수 없다 | 실행 중인 sandbox 에 새 포트를 열려면 재생성이 필요하다 |
| sandbox 는 5분 유휴 시 백업 후 **삭제**되고, 재개 시 **새 컨테이너**를 만들어 workspace 를 복구한다 | 프로세스는 모두 사라진다. 서버를 띄워 두는 방식은 유휴 종료 때마다 죽는다 |
| 전용 네트워크는 컨테이너 간 통신(icc)을 막는다 | 프록시 컨테이너로 sandbox 에 붙는 방식은 쓸 수 없다 (호스트→컨테이너는 영향 없음) |
| 사용자당 동시 실행 sandbox 상한이 5 개다 | 앱 때문에 개발 sandbox 가 밀려나면 안 된다 |
| workspace 백업은 1GB(`SANDBOX_BACKUP_MAX_MB`, 기본 1024) 상한이고 제외 규칙이 없다 | `node_modules` 가 큰 앱은 백업이 실패한다 |

## 3. 검토한 대안과 결정

### 3.1 노출 방식

| 안 | 내용 | 평가 |
|---|---|---|
| A. 개발 sandbox 컨테이너에서 서버를 띄우고 20000+ 포트를 직접 게시 | 서버형 앱 가능 | 컨테이너가 죽으면 포트도 사라져 **깨우기가 불가능**. 포트 게시는 생성 시점에 고정. 유휴 종료·백업/복구와 충돌 |
| B. dist 를 호스트로 복사해 정적 서빙 | 단순, 깨우기 불필요 | 서버형 앱 불가 |
| C. MinIO 공개 버킷 | 기존 인프라 재사용 | SPA 라우팅 폴백·앱별 포트 불가 |
| **D. 호스트 프록시 리스너(20000+) + 매핑 테이블 + 요청 시 깨우기** (채택) | 컨테이너가 없어도 포트는 유지, 서버형·정적 모두 가능 | 게이트웨이를 직접 구현해야 함 |

핵심 통찰: **20000~20100 은 Docker 게시 포트가 아니라 "프록시 리스너 포트"**다. 컨테이너가 꺼져 있을 때도 요청을 받아 깨우려면 포트를 계속 잡고 있는 쪽이 호스트의 게이트웨이여야 한다.

### 3.2 URL 방식: 포트 기반 vs 경로 기반

| | 포트 기반 (`:20001/`) | 경로 기반 (`/apps/{id}/`) |
|---|---|---|
| 앱의 base path | 루트에서 서비스 → 수정 불필요 | 앱이 하위 경로를 지원해야 함 (`base: './'`, 상대 경로 강제) |
| API 서버가 있는 앱 | 절대 경로 호출(`/api/..`)이 그대로 동작 | 절대 경로 호출이 깨짐 |
| 운영 | 방화벽에서 포트 범위를 열어야 함, 포트 수 한계 | 단일 진입점, TLS 종료 용이 |

→ **포트 기반을 기본**으로 채택. 경로 기반은 운영 단일 진입점이 필요할 때의 선택 기능으로 남겨 두었다 (§9 미구현).

### 3.3 배포 모델: 개발 sandbox 재개 vs 불변 아카이브 + 전용 컨테이너

| | 개발 sandbox 를 깨움 | **불변 아카이브 + 앱 전용 경량 컨테이너** (채택) |
|---|---|---|
| 시작 비용 | workspace 전체 복구 + 앱 시작 | 아카이브만 풀고 시작 |
| 개발 중 변경 | 서비스 중인 앱에 그대로 영향 | 영향 없음 (스냅샷) |
| sandbox 상한(5개) | 소모 | 소모하지 않음 |
| 버전 | 없음 | 버전 증가, 같은 이름 재배포 시 URL 유지 |
| 자원 | 일반 sandbox | 경량 (CPU 0.5, 512m) |

→ 참조 프로젝트(§4)의 "deploy sandbox" 모델을 채택했다.

### 3.4 컨테이너 포트 노출: "슬롯" 방식

- 컨테이너 생성 시 앱 포트를 `127.0.0.1` 의 **임시(ephemeral) 호스트 포트**로 게시하고(Docker 가 배정), 생성 직후 실제 포트를 읽어 레지스트리에 기록한다. 내부용 포트 범위를 따로 관리할 필요가 없다.
- 앱 전용 컨테이너는 **매번 새로 만들어지므로** 생성 시점에 게시하는 방식이 제약이 되지 않는다.
- Linux 운영에서는 컨테이너 IP 로 직접 연결하는 방식도 가능하다 (업스트림 해석기 어댑터 — 미구현, §9).
- 개발 sandbox 에 여러 포트 슬롯을 미리 게시하는 안은 **개발 미리보기(HMR)** 를 지원할 때 필요하다 (미구현, §9).

### 3.5 아카이브 저장 위치: MinIO vs 호스트 디스크

참조 프로젝트는 MinIO 에 올리고 컨테이너가 `curl` 로 내려받는다. 우리는 **호스트 디스크**(`data/apps/{id}/artifact.tar.gz`)에 두고, 시작할 때 Docker API(`put_archive`)로 직접 푼다.

- 컨테이너에 URL·자격 증명을 줄 필요가 없다 (사용자 코드가 도는 곳에 MinIO 키를 두지 않는다).
- 셸 문자열에 URL 을 끼워 넣지 않으므로 명령 주입 경로가 없다.
- 단점: 호스트가 여러 대면 공유가 안 된다 (§9).

## 4. 참조 구현 분석 (`skt_adot_super_agent_v2`)

`super_agent_proxy_server`(호스트 프록시)와 `sandbox_tools`(컨테이너 안의 HTTP 서버)를 읽고 비교했다.

**구조:** 브라우저 → 프록시(`/preview/{session}/…`, `/deploy/{id|slug}/…`, 단일 포트 8992) → `sandbox_server`(Nomad 오케스트레이터, `extra_ports["preview"]` 동적 포트) → 컨테이너(내부 5173 고정). 컨테이너 안의 `sandbox_tools` 가 exec/파일/snapshot(tar.gz→MinIO)/idle 감시/keepalive 를 담당한다.

**채택한 것**
- 배포 = 불변 아카이브 + 전용 경량 컨테이너
- `.scripts/start.sh` 처럼 정해진 스크립트만 실행하는 규약 (임의 명령 금지)
- 실패 쿨다운 + 재시도 상한, 상태 폴링 API(`/__app/status`)와 로딩 페이지
- 임시 게시 포트(Nomad 동적 포트의 Docker 대응), WebSocket 서브프로토콜 전달

**버린 것 / 개선한 것**

| 참조 구현의 문제(코드 근거) | 우리 구현 |
|---|---|
| 배포 깨우기가 로딩 페이지의 `/status` 폴링에만 의존. API 호출이 연결 실패하면 HTML 로딩 페이지를 받음 | 요청 시 깨우고, 브라우저(HTML)는 로딩 페이지, 그 외는 최대 25초 대기 후 JSON 503 |
| 상태(`_initializing`, `_failed`, 캐시)가 프로세스 메모리에만 있어 다중 워커에서 깨짐 | DB + 레지스트리, 시작 시 복구 (단, 단일 프로세스 전제 — §9) |
| `follow_redirects=True` 공용 클라이언트와 리다이렉트 재작성 로직이 공존 (재작성이 실행되지 않을 가능성, **추정**) | `follow_redirects=False` + `Location` 재작성 |
| 일반 HTTP 응답을 전부 메모리에 올림 (SSE 만 스트리밍) | 요청·응답 모두 스트리밍 (`aiter_raw`) |
| 준비 확인을 `lsof` exec 로 수행 (+30초 캐시) | 게시 포트로 HTTP 프로브 |
| 명령에 URL·스크립트를 따옴표로만 끼워 넣음 (`curl '{url}'`, `bash -c '{cmd}'`) | 인자 배열·`shlex.quote`, 아카이브는 Docker API 로 직접 전달 |
| `CORS *` + credentials, 프록시 인증 없음 | 접근 토큰 옵션, 앱 origin 에 CORS 미개방 |
| 컨테이너 안에 MinIO 기본 키(`minioadmin`)와 HTTP 서버 | 컨테이너에 자격 증명·추가 서버 없음 |
| sandbox 당 앱 1 개(포트 5173 고정) | 앱마다 전용 컨테이너 |
| 경로 기반이라 base path 규칙·오류 페이지 필요 | 루트 서비스 (경로 기반은 선택) |

## 5. 최종 아키텍처

```
브라우저
   │  http://{APP_PUBLIC_HOST}:20001/…            (앱마다 하나씩 열리는 프록시 리스너)
   ▼
게이트웨이 (백엔드 프로세스 안의 uvicorn 서버, 앱 포트당 1개)       app/services/app_gateway.py
   │ ① 접근 토큰 확인(비공개 앱)
   │ ② 컨테이너가 꺼져 있으면 깨움 (같은 앱의 동시 요청은 하나의 시작을 공유)
   │ ③ 스트리밍 포워딩 (HTTP / SSE / WebSocket)
   ▼
127.0.0.1:{Docker 가 배정한 임시 포트}  ──▶  앱 전용 컨테이너 :5173 (PORT)
                                              /workspace/deploy   ← 아카이브를 푼 곳
                                              /workspace/data     ← 호스트의 data/apps/{id}/data 바인드 마운트 ($DATA_DIR)
```

### 5.1 구성 요소

| 구성 | 파일 | 역할 |
|---|---|---|
| 모델 | `models/published_app.py` | `published_apps` 테이블 (포트, 버전, 상태, 토큰, 컨테이너 id 등) |
| 아카이브 | `services/app_artifact.py` | tar 검증·정규화, 정적 서버 스크립트 |
| 호스트 | `services/app_host.py` | 레지스트리, 리스너 관리, 깨우기, 유휴 종료 |
| 게이트웨이 | `services/app_gateway.py` | 앱별 ASGI 프록시 |
| 서비스 | `services/app_service.py` | 배포·시작·중지·삭제·로그 |
| API | `api/apps.py` | `/api/apps` |
| 도구 | `tools/app_tools.py` | `deploy_web_app`, `manage_web_app` |
| 컨테이너 | `sandbox/manager.py` | `create_app_container`, `put_archive_file`, `exec_detached` 등 |
| 화면 | `components/sandbox/DeployedApps.tsx`, `components/chat/AppPreviewPanel.tsx` | 앱 목록, 채팅 우측 iframe |

### 5.2 데이터 모델 (`published_apps`)

`id`, `user_id`, `conversation_id`, `name`(사용자별 유일), `kind`(static|server), `proxy_port`(유일), `container_port`, `version`, `artifact_size`, `status`(stopped|starting|running|failed), `error`, `retry_count`, `require_token`, `access_token`, `container_id`, `last_request_at`, `last_log`, 생성·수정 시각.

### 5.3 배포 흐름 (`deploy_web_app`)

1. 이름·경로 검증, 사용자당 앱 수 상한 확인.
2. 대화방 sandbox 에서 디렉터리를 꺼냄 (`export_path`). 종류 판별: `.scripts/start.sh` 가 있으면 server, 없으면 `index.html` 이 있는 static.
3. 아카이브 검증·정규화 (최상위 디렉터리 제거, 소유자 1000). 절대 경로·`..`·밖을 가리키는 링크·장치 파일 거부, 크기(200MB)·파일 수(50000) 상한.
4. 가장 낮은 빈 포트를 배정 (DB 유니크 + 실제 바인드 가능 확인, 락으로 동시 배정 보호). 같은 이름이면 포트 유지, 버전만 증가.
5. 리스너를 열고, 앱을 시작해 준비될 때까지 기다린 뒤 URL 을 반환한다 (실패하면 로그 끝부분을 함께 반환).

### 5.4 깨우기 (wake-on-request)

- 앱 컨테이너는 **요청이 오면** 생성된다: 컨테이너 생성(포트 게시) → 아카이브 풀기 → 시작 명령 실행 → HTTP 로 준비 확인(최대 60초).
- 시작 명령: static = 내장 Python 정적 서버(SPA 폴백, 디렉터리 목록 없음), server = `bash .scripts/start.sh` (환경변수 `PORT`, `DATA_DIR`, `HOST`).
- 단일 비행: 같은 앱의 동시 요청은 하나의 시작 Task 를 공유한다.
- 응답 정책: 브라우저(HTML GET)는 503 + 자동 새로고침 로딩 페이지, 그 외는 `APP_WAKE_WAIT_SECONDS`(25초)까지 대기 후 전달 또는 JSON 503.
- 실패: 상태 `failed` + 오류·로그 보관, 쿨다운(30초)과 재시도 상한(3회) 후에는 수동 시작/재배포가 필요하다.
- 유휴: 요청이 `APP_IDLE_MINUTES`(10분) 없으면 컨테이너를 삭제한다 (데이터 디렉터리와 아카이브는 남는다).
- 백엔드 재시작: 시작 시 DB 의 앱을 올리고 리스너를 연다. 컨테이너가 살아 있으면 이어서 쓰고, 아니면 `stopped`.

### 5.5 앱 규약 (에이전트·사용자용)

- **정적 앱:** 빌드 결과 디렉터리(`index.html` 포함)를 지정. 루트에서 서비스되므로 Vite `base` 기본값(`/`)으로 충분하다.
- **서버형 앱:** 디렉터리에 `.scripts/start.sh` 필요. 서버는 `0.0.0.0:$PORT` 에서 들어야 하고, 영구 데이터는 `$DATA_DIR` 에 저장한다. 아카이브는 의존성을 포함한 **자체 완결형**이어야 한다 (시작 시 네트워크 설치는 `start.sh` 가 직접 하는 경우에만).
- **실행 환경:** 앱 컨테이너는 sandbox 이미지(`ai-agent-sandbox`, 또는 `APP_IMAGE`)를 쓴다. Node.js 22(node/npm/npx), **Bun**(bun/bunx), Python 3.12 가 들어 있고, 그 밖의 런타임은 아카이브에 포함해야 한다. 이미지를 바꾼 뒤에는 `docker build -t ai-agent-sandbox:latest sandbox-image` 로 다시 만들어야 새로 만들어지는 앱 컨테이너에 반영된다 (이미 실행 중인 컨테이너는 그대로).
- 같은 이름으로 다시 배포하면 같은 URL 에 새 버전이 올라간다.

### 5.6 보안 설계

| 위협 | 대응 |
|---|---|
| 아카이브를 통한 경로 이탈·링크·장치 파일 | `normalize_archive` 에서 거부 |
| 명령 주입 | 아카이브를 Docker API 로 전달, 셸 문자열에 외부 값을 넣지 않음 |
| 프록시 SSRF | 업스트림은 서버가 기록한 `127.0.0.1:{게시 포트}` 만 사용, 요청 값으로 목적지를 정하지 않음 |
| 포트가 추측 가능 (20000~20099) | 비공개 앱은 소유자 전용: 메인 앱이 발급한 일회용 실행 티켓(§10)이 있어야 열린다 (이전의 링크 토큰 방식은 폐기) |
| 앱 코드의 메인 앱 접근 | 포트가 달라 origin 분리 (메인 앱 JWT 가 localStorage 라면 읽을 수 없음), CORS 미개방 |
| 컨테이너 격리 | 기존 sandbox 와 동일: `cap_drop ALL`, `no-new-privileges`, 메모리 512m, CPU 0.5, 전용 네트워크 |
| 남용 | 사용자당 앱 수 상한(5), 아카이브 크기·파일 수 상한, 외부 공개 도구는 메신저 승인 대상(`RISKY_TOOLS`) |
| 컨테이너 안의 자격 증명 | 없음 |

### 5.7 UI

- **샌드박스 메뉴 → 배포된 앱:** 상태, URL, 복사, 로그, 시작·중지, 삭제. (배포 자체는 채팅에서 에이전트가 수행한다. 화면에서 배포하는 버튼은 없다.)
- **채팅 우측 패널:** `deploy_web_app` 성공 결과(`Open: URL`)를 감지하면 iframe 미리보기 패널을 자동으로 열고, 헤더에 **앱** 버튼이 생긴다. 새로고침과 새 창 열기 버튼 포함.

### 5.8 설정 (`.env`)

`APP_HOST_ENABLED`, `APP_PORT_START`, `APP_PORT_END`, `APP_BIND_HOST`(기본 127.0.0.1), `APP_PUBLIC_HOST`(기본 localhost), `APP_CONTAINER_PORT`, `APP_MAX_PER_USER`, `APP_ARTIFACT_MAX_MB`, `APP_ARTIFACT_MAX_FILES`, `APP_DATA_DIR`, `APP_IDLE_MINUTES`, `APP_STARTUP_TIMEOUT`, `APP_WAKE_WAIT_SECONDS`, `APP_IMAGE`, `APP_MEMORY_LIMIT`, `APP_CPU_LIMIT`, `APP_FAILURE_COOLDOWN`, `APP_MAX_RETRIES`. 기본값은 `backend/app/config.py`, 예시는 `.env.example`.

**원격 서버로 외부 공개할 때:** `APP_BIND_HOST=0.0.0.0`, `APP_PUBLIC_HOST=서버 주소`, 방화벽에서 포트 범위 개방. 비공개 앱은 소유자 세션이 있어야만 열리므로 외부에 열어도 안전하다. 공개 앱은 §10 의 와일드카드 도메인 설정이 필요하다.

## 6. 검증한 것

실제 Docker 와 실행 중인 서버에서 확인했다 (임시 사용자 생성 후 정리).

- 정적 앱: 루트 응답, SPA 폴백(없는 경로 → `index.html`), 정적 자산.
- 서버형 앱(Node): API 응답, **중지 후 JSON 요청으로 깨우기 → `$DATA_DIR` 의 카운터가 이어짐** (데이터 유지).
- 비공개 앱: 티켓 없이 401, 실행 티켓으로 303 + 쿠키, 쿠키로 접속 (자세한 검증은 §10).
- 같은 이름 재배포: 같은 포트·URL, 버전 증가.
- 삭제: 컨테이너·포트 정리 확인.
- 단위 테스트: 아카이브 검증(안전하지 않은 항목 거부, 한도), 포트 할당(최저 빈 포트·고갈), 토큰 판정, `Location` 재작성 등.
- 프론트엔드 타입 체크, URL 추출 정규식.

## 8. 알려진 한계

- **정적·서버형만** 지원한다. 개발 서버(HMR) 미리보기는 지원하지 않는다 (§9).
- 리스너가 **백엔드 프로세스 안**에서 돈다. gunicorn 워커가 여러 개면 포트가 한 워커에만 묶인다.
- 백엔드를 재시작하면 리스너가 잠깐 끊긴다 (시작 시 복구).
- 포트 범위가 101 개라 전체 사용자 합계가 그 이하여야 한다.
- 아카이브는 앱당 **최신 1 개만** 보관한다 (롤백 불가).
- 서버형 앱이 `/workspace/deploy` 에 쓰는 파일은 컨테이너와 함께 사라진다 (영구 데이터는 `$DATA_DIR`).
- 메인 앱이 `https` 이고 앱 URL 이 `http` 이면 브라우저가 iframe 을 차단한다 (혼합 콘텐츠).
- 메인 앱과 앱의 **도메인이 다르면** iframe 안에서 토큰 쿠키(SameSite=Lax)가 전달되지 않는다. 새 창에서 열어야 한다.
- 앱이 스스로 `X-Frame-Options`/CSP `frame-ancestors` 를 보내면 iframe 에 표시되지 않는다.

## 9. 향후 검토 과제

우선순위는 제안이다. (상) 운영 전 필수, (중) 사용성·안정성, (하) 필요 시.

### 운영 구성
- (상) **게이트웨이 분리:** 다중 워커 운영을 위해 리스너를 별도 프로세스(`app-gateway`)로 분리하고 DB 를 단일 진실 원천으로 둔다. 또는 nginx 서버 블록을 자동 생성하고 `nginx -s reload`.
- (상) **원격 서버 구성 확정:** 외부 호스트명, 방화벽 포트 범위, 토큰 필수 정책, HTTPS(리버스 프록시)와 iframe 혼합 콘텐츠 문제.
- (중) **업스트림 해석기 어댑터:** Linux 운영에서는 게시 포트 대신 컨테이너 IP 로 직접 연결 (포트 게시 불필요).
- (중) **경로 기반 URL(`/apps/{slug}/`) 선택 기능:** 단일 진입점이 필요할 때. 이 경우에만 base path 규칙(`base: './'`, 상대 경로)과 리다이렉트 이탈 오류 페이지가 필요하다.
- (하) 앱별 slug·사용자 지정 도메인.

### 보안·접근 제어
- (상) **깨우기 남용 방지:** 인증되지 않은 요청이 컨테이너 생성을 유발하지 못하게 토큰 검증을 깨우기 앞에 두었는지 점검하고, 앱별 깨우기 횟수 제한·전체 동시 깨우기 상한을 추가한다.
- (중) **토큰 재발급(rotate)** 과 공유 링크 만료.
- (중) **관리자 강제 중지/차단 기능**, 앱별 요청률·동시 연결 수 제한.
- (중) 쿠키 설정 점검: 도메인이 다른 iframe 에서도 쓰려면 `SameSite=None; Secure`(HTTPS 필요).
- (하) 앱 전용 egress 제한 (현재 sandbox 와 동일하게 외부 인터넷 허용).

### 앱 실행 모델
- (상) **의존성 처리 정책:** 서버형 앱에 `node_modules` 를 아카이브에 포함할지, 깨울 때 `npm ci` 를 할지. 시작 시간과 크기 한도의 균형을 정해야 한다.
- (중) **프로세스 감시:** 앱이 죽었을 때 재시작(횟수 제한)과 크래시 로그 보존. 현재는 연결 거부를 감지하면 `stopped` 로 돌려 다음 요청이 다시 깨운다.
- (중) **keep-warm:** 앱별 `keep_warm_minutes` 로 콜드 스타트를 피할 수 있게 한다 (현재 전체 유휴 시간 하나).
- (중) **앱별 환경변수·시크릿** 관리 (암호화 저장, 예: MCP env 의 Fernet 방식).
- (중) **버전 보관·롤백:** 이전 아카이브를 N 개 보관하고 되돌리기.
- (중) **데이터 디렉터리 백업/복구**와 용량 상한 (`data/apps/{id}/data`).
- (하) 개발 미리보기(HMR): 개발 sandbox 에 여러 포트 슬롯을 미리 게시하고 Vite 설정 wrapper(`server.hmr.path`)를 주입하는 참조 구현 방식.

### 관측성·운영
- (중) **로그 영속화:** 현재는 컨테이너 삭제 시 마지막 4KB 만 `last_log` 에 남는다. 로그 스트리밍·보존 정책이 필요하다.
- (중) **지표:** 앱별 요청 수·지연·콜드 스타트 시간·실패 횟수 (Prometheus).
- (중) **콜드 스타트 측정과 개선:** 이미지 경량화(앱 전용 이미지), 아카이브 풀기 최적화.
- (하) 아카이브를 MinIO 로 옮길지 (호스트가 여러 대가 될 때).

### 정책·자원
- (중) **포트 고갈 대응:** 범위(101 개) 확대, 사용자별 쿼터, 오래 쓰지 않은 앱의 자동 정리(삭제 전 알림).
- (중) **동시 실행 상한 정책:** 앱 컨테이너 수 상한(전체·사용자별)과 개발 sandbox 상한(5)의 관계.
- (하) 앱 소유권 이전·팀 공유.

### 테스트·문서
- (상) **통합 테스트 자동화:** 지금의 E2E 는 수동 스크립트다. Docker 가 있는 환경에서 정적/서버형 배포, 깨우기, 토큰, 재배포를 자동 검증하는 테스트를 추가한다.
- (중) 게이트웨이 단위 테스트 확대 (WebSocket 중계, 스트리밍, 실패 쿨다운).
- (중) 에이전트용 **앱 작성 가이드**(스크립트 템플릿, `$PORT`/`$DATA_DIR` 규약, 자체 완결형 아카이브)를 스킬이나 프롬프트로 제공.
- (하) 화면에서 직접 배포하는 UI (대화방·경로 선택 후 `POST /api/apps`).

### 마이그레이션
- (중) Alembic 체인 정리(충돌 표시 해결, 단일 헤드 복구는 완료)와 DB 버전 표시를 실제 상태에 맞추는 작업. 지금은 `create_all` 과 컬럼 보강 코드가 실제 스키마를 만든다.

## 10. 접근 제어와 App Store (비공개 / 공개)

배포된 앱은 **기본 비공개(소유자만)** 이고, App Store 에 등록하면 **공개(로그인 없이 누구나 접속)** 가 된다.

### 10.1 결정 사항

| 결정 | 내용 |
|---|---|
| 익명 접속 | 허용. 대신 요청률·깨우기 횟수 제한, 전체 실행 상한을 둔다 |
| 공개 앱 URL | **호스트명 라우팅**: `http://{slug}.localhost:20100/` — 포트 하나에서 `Host` 헤더로 앱을 구분 (포트 고갈·쿠키 격리 문제 해소) |
| 비공개 앱 URL | 기존 포트 방식(20000~20099) 유지 |
| 서버형 앱 공개 | 관리자 승인 후 공개 (`moderation_status=pending`). 정적 앱은 자동 점검 통과 시 즉시 공개 |
| 재배포 | 공개 중인 앱의 새 버전은 다시 점검한다 (걸리면 비공개로 되돌림, 서버형은 다시 승인 대기) |
| 공개 앱의 인스턴스 | 방문자 전원이 하나의 인스턴스·데이터 디렉터리를 공유 (설치형 복사본은 후속 과제) |
| 링크 토큰 공유 | 제거 (필요하면 중간 단계로 나중에 추가) |

### 10.2 비공개 = 소유자만: 실행 티켓

앱은 다른 origin 이라 메인 앱의 로그인 정보를 알 수 없다. 메인 앱이 소유자를 확인하고 서명한 **일회용 티켓(60초)** 을 URL 로 넘기면 게이트웨이가 이를 **세션 쿠키**(`appsess_{port}`, HttpOnly, 8시간)로 교환한다.

1. `POST /api/apps/{id}/launch` (소유자 인증) → `http://localhost:{port}/?t={ticket}` 반환
2. 게이트웨이: 서명(HMAC-SHA256, `SECRET_KEY`)·만료·앱·소유자·**일회 사용** 검증 → 쿠키 발급 → 티켓 없는 주소로 303
3. 티켓·세션이 없는 직접 접속은 401 ("My Apps 에서 실행하세요")
4. 앱의 `session_epoch` 를 올리면 발급된 세션이 모두 무효화된다
5. 소유자 세션 쿠키(`appsess_*`)는 어떤 앱에도 전달하지 않는다 (같은 호스트의 다른 포트 앱이 받을 수 있기 때문)

그래서 채팅 우측 iframe·My Apps 는 **열 때마다 `launch` 를 호출**한다. 에이전트의 도구 결과에는 URL 대신 `App ID` 만 담는다.

### 10.3 공개 = App Store

- 등록: `POST /api/apps/{id}/publish` (제목·설명·카테고리·태그·**약관 동의**). 사람만 할 수 있고 에이전트 도구는 없다.
- 등록 전 **자동 점검**: 비밀 파일 이름(`.env`, `*.pem`, `id_rsa`…), 코드·설정 안의 키/토큰 패턴(`sk-`, `AKIA`, `ghp_`, 개인 키 등). `node_modules` 와 큰 파일·바이너리는 건너뜀. 걸리면 등록 거부.
- 공개 게이트웨이는 `visibility=public` **그리고** `moderation_status=approved` 인 앱만 서비스한다. 그 외는 404.
- 등록 취소(`unpublish`)는 즉시 익명 접속을 막고 스토어 목록에서 뺀다 (데이터 보존).
- 신고: 서로 다른 사용자의 신고가 `APP_REPORT_SUSPEND_THRESHOLD`(3) 건이면 **자동 정지**(서비스 중단 + 컨테이너 종료) 후 관리자 검토.
- **검수(승인 페이지 `/store/review`):** 승인 대기·정지(신고)·공개 중·반려 큐에서 승인/반려/정지(반려·정지는 사유 필수, 소유자에게 표시). **미리보기**는 검수용 일회용 티켓(60초)으로 승인 전·정지된 앱도 공개 호스트명으로 열어 볼 수 있게 한다 (티켓 → `appreview` 세션 쿠키, 1시간). 검수 세션은 소유자 세션·티켓과 종류가 달라 서로 대신할 수 없다.
- **검수 권한:** 사용자 역할이 아직 없어 현재는 **로그인한 모든 사용자**가 검수할 수 있다(`APP_REVIEW_OPEN_TO_ALL=true`). 역할을 도입하면 `false` 로 바꾸고 `ADMIN_EMAILS` 로 제한한다. `APP_REVIEW_ALLOW_SELF=false` 면 자기 앱은 검수할 수 없다 (모든 사용자가 검수자인 동안은 자기 승인으로 승인제를 우회할 수 있으므로 역할 도입 시 함께 끌 것).

### 10.4 공개 앱의 방어

| 위협 | 대응 |
|---|---|
| 쿠키 오염 | 앱마다 호스트명이 달라 쿠키가 분리된다 (포트 방식은 쿠키를 공유함) |
| 익명 요청으로 컨테이너 생성(DoS) | 앱별 분당 깨우기 상한(`APP_PUBLIC_WAKE_PER_MIN`), 이미 시작 중이면 합류 |
| 과도한 요청 | IP·앱별 분당 요청 상한(`APP_PUBLIC_RATE_PER_MIN`) → 429 |
| 컨테이너 과다 | 전체 실행 상한(`APP_MAX_RUNNING`), 가장 오래 쓰지 않은 앱을 내림 |
| MIME 스니핑 | 공개 응답에 `X-Content-Type-Options: nosniff` |
| 임베드된 공개 앱의 탈출 | iframe `sandbox` 에 `allow-top-navigation` 없음 |
| 비밀 유출 | 등록 전 자동 점검 |
| 악성 앱 | 신고 → 자동 정지, 관리자 검수, 서버형은 승인제 |

### 10.5 구성 요소 (추가·변경)

`services/app_auth.py`(티켓·세션), `services/app_policy.py`(slug, 공개 URL, 점검, 요청률 제한), `services/app_gateway.py`(port/public 두 모드), `services/app_host.py`(공개 리스너·전체 상한), `services/app_service.py`(publish·moderate·report), `api/store.py`, `api/apps.py`(launch·publish), `pages/StorePage.tsx`, `pages/MyAppsPage.tsx`, `components/apps/PublishDialog.tsx`. 컬럼·테이블은 `published_apps`(visibility, slug, session_epoch, moderation_*, title, description, category, tags, listed_at, launch_count)와 `app_reports`. 별도 listing 테이블 없이 한 테이블에 두었다.

### 10.6 운영 설정

- `APP_PUBLIC_DOMAIN`/`APP_PUBLIC_SCHEME`/`APP_PUBLIC_PORT`: 운영에서는 와일드카드 DNS(`*.apps.example.com`)와 TLS 를 리버스 프록시(nginx 등)에서 종료하고 `APP_PUBLIC_PORT` 로 넘긴다. 로컬 `*.localhost` 는 Chrome/Firefox 에서 동작하며 Safari 는 풀리지 않을 수 있다.
- `ADMIN_EMAILS`: 검수 권한자 (비어 있으면 아무도 검수할 수 없다).
- 리버스 프록시 뒤에서는 클라이언트 IP 가 프록시 주소로 보이므로, 요청률 제한이 의미를 가지려면 신뢰하는 프록시의 `X-Forwarded-For` 처리(미구현)가 필요하다.

### 10.7 검증 (실제 서버, Docker)

비공개 직접 접속 401 → 실행 티켓 303 + 쿠키 → 티켓 재사용 401 → 다른 사용자의 launch 404 → 약관 미동의·비밀 파일 포함 등록 거부 → 정적 앱 등록 즉시 공개, **익명 접속(Host 헤더) 성공**, 엉뚱한 Host 404, 공개 앱의 포트 직접 접속은 여전히 401 → 스토어 목록·열기(접속 수 증가)·신고 → 비관리자의 검수 API 403 → 서버형 앱 등록은 승인 대기이며 승인 전 공개 호스트 404, 스토어 목록 제외 → 등록 취소 즉시 404. 점검·티켓·요청률·slug/Host 해석은 단위 테스트.

### 10.8 미검증·후속

- 관리자 승인/반려/정지 API 의 실제 호출(`ADMIN_EMAILS` 를 설정한 환경에서)과 신고 3건 자동 정지 흐름은 단위 수준까지만 확인했다.
- 화면(스토어·My Apps·등록 대화상자·검수 탭)은 타입 체크만 했고 브라우저에서 확인하지 않았다.
- 공개 앱을 실제 `{slug}.apps.<도메인>` + HTTPS 로 서비스하는 구성, 프록시 뒤 클라이언트 IP, 공개 앱의 egress 제한, 서버형 앱 공개 시의 추가 격리, 스크린샷·아이콘 업로드, 접속 수 중복 제거는 후속 과제다.
- 이미 만들어진 앱은 시작 시 컬럼 보강 코드로 `private` 이 된다 (이전에 토큰 없이 열려 있던 앱도 소유자 전용으로 바뀐다).
