# 사이트 요령 (브라우저 에이전트 리소스)

사이트마다 달라지는 사용법(검색·정렬 주소, 알려진 함정)을 프롬프트가 아니라 **데이터**로 둔다. 사이트 UI가 바뀌면 그 내용만 고친다.
두 층으로 나눈다.

- **분야(vertical) 공통 지침** `verticals/*.md`: 쇼핑·영화·항공·호텔처럼 분야 안에서 사이트와 상관없이 같은 것. 진행 순서, 보고 항목, 멈출 지점(결제 직전), 새 사이트를 분석할 때 확인할 체크리스트.
- **사이트별 요령** `sites/*.md`: 그 사이트에서만 맞는 것. 검색·정렬 주소, 화면 구조, 로그인·캡차, 함정.

## 원본과 md 파일의 관계

원본은 **DB**(`site_verticals`, `site_profiles`)이다. 이 폴더의 md 는 **시드**다: 서버가 시작할 때 DB 에 없는 분야·사이트만 채우고, 이미 있는 것(화면에서 고친 것 포함)은 덮어쓰지 않는다.
런타임은 DB 내용을 메모리 캐시로 읽고(`services/site_profile_service.py`), DB 를 읽지 못하면 이 md 파일을 그대로 쓴다. 그래서 md 를 고쳐도 이미 시드된 DB 의 내용은 바뀌지 않는다.

`app/agent/site_tips.py` 가 읽어서 작업에 해당하는 것만 브라우저 에이전트에게 준다.

- **시작할 때**: 작업의 시작 URL·작업 문장의 주소·사이트 이름에 맞는 사이트 요령과 그 사이트의 분야 지침, 그리고 작업 문장에 분야 키워드가 나오는 분야 지침을 지침 끝에 붙인다.
- **이동할 때**: 에이전트가 처음 방문하는 도메인에 맞는 요령이 있으면 그 이동 결과 끝에 한 번만 덧붙인다 (분야 지침이 아직 안 나갔으면 함께).
- **결제 직전 중단**: 결제·주문 확정 라벨(`결제하기` 등)과 결제 주소는 모든 분야에서 막는다. 분야 파일의 `stop_words`/`stop_urls` 는 그 분야에서 더 막을 라벨·주소 문구다 (예: 쇼핑의 `구매하기`).

## 분야 파일 형식 (`verticals/*.md`)

```
---
key: flight                 # 필수. 영문 소문자. 사이트 파일의 vertical 과 같은 값
name: 항공권                 # 필수
keywords: 항공권, 항공편      # 쉼표 구분. 작업 문장에 나오면 이 분야 지침을 붙인다 ('영화' 처럼 흔한 단어는 피한다)
stop_words: 예약 확정         # 쉼표 구분. 이 문구가 들어간 짧은 버튼은 누르지 않는다
stop_urls:                  # 쉼표 구분. 이 문구가 주소에 있으면 이동하지 않는다
---
에이전트에게 주는 공통 지침 (진행 순서, 주의, 보고 항목)

## 분석 체크리스트
- 새 사이트를 분석할 때 확인할 질문 (에이전트에게는 주지 않는다)
```

## 사이트 파일 형식 (`sites/*.md`)

```
---
name: 다나와                # 필수. 화면·안내에 쓰는 이름
domains: danawa.com         # 필수. 쉼표로 여러 개. 하위 도메인(search.danawa.com)도 맞는다
vertical: shopping          # 선택. 분야 key
aliases: 다나와              # 선택. 작업 문장에서 이 단어가 나오면 시작할 때 붙인다 ('다음' 처럼 흔한 단어는 피한다)
status: draft               # 선택. draft 는 분석 전 자리만 만든 것이라 에이전트에게 주지 않는다 (생략하면 verified)
verified: 2026-11-09        # verified 일 때 필수. 이 요령을 마지막으로 직접 확인한 날짜 (낡은 요령 구분용)
---
본문 (에이전트에게 그대로 전달된다. 주소 템플릿은 `검색어` 자리표시자를 쓴다)
```

- 확인한 것만 적는다. 추측·일반론은 프롬프트(`prompts/browser_agent.md`)나 분야 지침에 둔다.
- 새 파일을 추가하면 `tests/unit/test_site_tips.py` 가 형식(필수 항목, 날짜, 도메인 중복, 분야 참조)을 검사한다.

## 구조화(spec): 입력값·플로우·메뉴 지도

자유 서술만으로는 "어떤 값을 넣고, 어느 메뉴로 가서, 어떤 순서로 하는가"를 비교·검증할 수 없어서, md 본문 앞에 ` ```spec ` 코드 블록(JSON)으로 구조를 둔다. 검증·정리는 `app/agent/site_spec.py`, 에이전트에게 주는 텍스트도 거기서 풀어 쓴다.

- **분야** `{inputs: [{key, label, required, format, example}], flow: [{key, title, desc, write}], sample: {입력키: 값}}`: 이 분야 작업에 필요한 입력값, 표준 진행 단계(`write: true` 는 장바구니·좌석·예약처럼 상태를 바꾸는 단계라 분석·검증에서 시험하지 않는다), 재현 검증에 쓸 샘플 값.
- **사이트** `{entry: [{label, url}], menus: [{name, path, url}], inputs: {입력키: {how, param}}, flow: [{key, how, url}], stop_point}`: 진입·직접 이동 주소(입력값 자리는 `{입력키}`), 메뉴·화면 지도, 분야의 입력값을 이 사이트에서 넣는 방법, 분야의 표준 단계를 이 사이트에서 수행하는 방법, 멈출 지점. `inputs`·`flow` 의 키는 분야가 정의한 키를 따른다.
- md 본문은 구조에 담기지 않는 예외·함정만 적는다. 구조가 비어 있어도(에누리처럼) 본문만으로 동작한다.
- 분석(`site_analysis.md`)은 `<구조>{사이트 spec}</구조>` 로 초안을 내고, 재현 검증(`site_verify.md`)은 분야의 샘플 입력값으로 표준 단계를 수행해 단계별(`reached`/`failed`/`skipped`) 결과를 보고한다. 통과 조건: 성공 보고 + 읽기 단계가 모두 `reached` + 반복 차단 2회 이하.
- 구조화 이전에 DB 에 시드된 행(`source=seed`)은 서버가 시작할 때 md 의 spec 으로 채운다. 화면에서 고친 행은 건드리지 않는다.

## 수정 이력과 웹사이트 분석 (화면: 맞춤 설정 → 웹사이트 분석)

- **수정 이력**: 분야·사이트를 저장할 때마다 저장 후의 상태가 `site_profile_revisions` 에 남는다 (항목마다 최근 50개). 이력이 없던 항목(시드 직후)은 처음 고칠 때 고치기 전 상태도 함께 남긴다. 화면에서 버전을 고르면 지금 내용과의 차이를 보고 되돌릴 수 있고, 되돌린 것도 새 버전으로 이력에 남는다.
- **사이트 분석**(`services/site_analysis_service.py`): 에이전트가 시작 주소에서 시나리오를 읽기 전용으로 수행하며 분야의 *분석 체크리스트*를 확인하고 요령 초안을 만든다 (`prompts/site_analysis.md`). 로그인·장바구니·예약·결제는 실행하지 않고, 결제 직전 중단 가드도 그대로 적용된다.
- **재현 검증**(`prompts/site_verify.md`): 초안을 저장하기 전에 요령으로 주고 같은 시나리오를 다시 수행시킨다. 에이전트가 성공을 보고하고 반복 차단이 2회 이하일 때 '통과'이며, 통과한 초안만 화면에서 '검증됨으로 저장'할 수 있다. 판정은 에이전트의 보고에 기대므로 화면의 스크린샷으로 마지막 화면을 직접 확인한다.
- 한 사용자가 동시에 하나만 실행할 수 있다. 데스크톱 앱에 연결된 사용자는 내 브라우저에서, 아니면 서버 브라우저에서 실행된다.
